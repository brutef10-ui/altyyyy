# Luminous — квиз-игра в реальном времени

Ведущий выводит вопросы на большой экран, игроки отвечают с телефонов. Проект состоит из трёх независимых частей:

| Часть | Что делает | Порт по умолчанию |
|---|---|---|
| `server/` | Node.js + Express + Socket.IO + PostgreSQL. Вся игровая логика, таймер и подсчёт очков, аккаунты ведущих, REST API для сохранённых игр | 3000 |
| `host-site/` | Сайт ведущего: вход и регистрация, список игр, редактор, лобби, экран игры, итоги | 5500 |
| `player-site/` | Сайт игрока: код комнаты → селфи → ник → игра | 5501 |
| `admin-site/` | Админ-консоль: аккаунты, гости, блокировки, журнал аудита. Отдаёт сам сервер по адресу `/admin/` и только администратору | — |

Сайты ничего не знают друг о друге и общаются только с сервером. Клиентам сервер не доверяет: правильные ответы, время и очки знает только он.

Создавать и запускать игры (в том числе демо) может только вошедший ведущий; игроку аккаунт не нужен — он входит по коду комнаты. Аккаунты, сессии, игры и картинки хранятся в PostgreSQL. План и ход работ по аккаунтам, админ-консоли, журналам и блокировкам — в [`docs/ACCOUNTS_PLAN.md`](docs/ACCOUNTS_PLAN.md).

## Установка и запуск

Нужен **Node.js 22+** (на Render — 24) и **PostgreSQL 13+**.

### База данных

Сервер не запустится без `DATABASE_URL`: аккаунты, сессии, игры и картинки хранятся в PostgreSQL.
Таблицы создаются сами при первом запуске (миграции из `server/migrations/`).

```bash
# Например, через Docker:
docker run -d --name luminous-db -e POSTGRES_PASSWORD=postgres -p 5432:5432 postgres:16
docker exec luminous-db createdb -U postgres luminous
docker exec luminous-db createdb -U postgres luminous_test   # для тестов

cd quiz-project/server
cp .env.example .env
# в .env:  DATABASE_URL=postgresql://postgres:postgres@localhost:5432/luminous
```

Администратор задаётся только в `.env` (или в настройках Render): `ADMIN_LOGIN` и `ADMIN_PASSWORD_HASH` —
хэш пароля, а не сам пароль. Получить хэш: `cd server && npm run hash-password` (пароль вводится скрытно).

### Всё одной командой

```bash
cd quiz-project
npm install          # установит зависимости сервера
npm run dev          # сервер :3000, сайт ведущего :5500, сайт игрока :5501
```

Откройте http://localhost:5500 — это экран ведущего. Игроки заходят на http://localhost:5501.

### По отдельности (три терминала)

```bash
# 1. Сервер
cd quiz-project/server
cp .env.example .env     # при необходимости поправьте адреса
npm install
npm start                # или npm run dev — с перезапуском при изменениях

# 2. Сайт ведущего
cd quiz-project
node tools/serve.js host-site 5500

# 3. Сайт игрока
cd quiz-project
node tools/serve.js player-site 5501
```

Сайты — обычная статика: вместо `tools/serve.js` подойдёт любой веб-сервер (`npx serve`, nginx, Live Server в VS Code). Открывать HTML-файлы напрямую через `file://` нельзя — нужны ES-модули и HTTP.

### Одним процессом (режим `SERVE_SITES`)

```bash
cd quiz-project
npm install
npm run single
```

Сервер сам отдаёт оба сайта на одном порту: сайт игрока — http://localhost:3000/, сайт ведущего — http://localhost:3000/host/. CORS настраивать не нужно. Этот же режим используется для деплоя одним сервисом (`render.yaml`) и для запуска на телефоне.

### На Android-телефоне (Termux)

1. Установите **Termux** из F-Droid (https://f-droid.org/packages/com.termux/) — версия в Google Play устарела.
2. В Termux:
   ```bash
   pkg update -y && pkg install -y nodejs-lts git
   git clone -b claude/interactive-quiz-game-o8s0kx https://github.com/brutef10-ui/altyyyy
   cd altyyyy/quiz-project
   npm install
   npm run single
   ```
3. В Chrome откройте http://localhost:3000/host/ — экран ведущего, а в новой вкладке http://localhost:3000/ — экран игрока. На `localhost` камера работает.
4. Не закрывайте Termux. Чтобы Android не остановил сервер в фоне, в шторке уведомлений Termux нажмите «Acquire wakelock». Остановить сервер — `Ctrl` + `C` (кнопка CTRL на панели Termux, затем C).

Чтобы друзья в той же Wi-Fi сети играли со своих телефонов, узнайте IP телефона (Настройки → Wi-Fi → ваша сеть, например `192.168.1.5`) и запустите так:

```bash
PLAYER_SITE_URL=http://192.168.1.5:3000 npm run single
```

Игроки открывают `http://192.168.1.5:3000`. По обычному `http://` браузер не включит камеру на странице, поэтому у них будет кнопка «Загрузить фото» — на телефоне она откроет фронтальную камеру. Для селфи прямо на странице нужен HTTPS — см. деплой на Render.

Обновить код до последней версии: `cd altyyyy && git pull`, затем снова `cd quiz-project && npm install && npm run single`.

### Настройка `.env`

| Переменная | Назначение | По умолчанию |
|---|---|---|
| `PORT` | порт сервера | `3000` |
| `HOST_SITE_ORIGIN` | адрес сайта ведущего (CORS). Несколько — через запятую | `http://localhost:5500,http://127.0.0.1:5500` |
| `PLAYER_SITE_ORIGIN` | адрес сайта игрока (CORS). Несколько — через запятую | `http://localhost:5501,http://127.0.0.1:5501` |
| `PLAYER_SITE_URL` | публичный адрес сайта игрока, его видно в лобби и в QR-коде | первый из `PLAYER_SITE_ORIGIN` |
| `SERVE_SITES` | `true` — сервер сам отдаёт оба сайта (`/` и `/host/`) | `false` |
| `DATABASE_URL` | адрес PostgreSQL (**обязательно**) | — |
| `DATABASE_SSL` | `disable` / `require` / `verify` | `disable` для localhost и внутренней сети Render, иначе `require` |
| `SESSION_SECRET` | секрет для CSRF-токенов, от 32 символов (**обязательно на Render**) | случайный на время работы процесса |
| `COOKIE_SECURE` | cookie только по HTTPS | `true` на Render и при `NODE_ENV=production` |
| `SESSION_IDLE_DAYS`, `SESSION_ABSOLUTE_DAYS` | сессия истекает без активности / не живёт дольше | `14`, `60` |
| `REGISTRATIONS_PER_IP_PER_HOUR`, `REGISTRATIONS_PER_HOUR` | защита от массовых регистраций | `5`, `300` |
| `RECOVERY_CODE_TTL_MINUTES` | сколько действует одноразовый код восстановления от администратора | `60` |
| `EVENTS_ANONYMIZE_DAYS`, `EVENTS_DELETE_DAYS` | журнал заходов: обезличить (IP → /24 или /48, без user-agent) / удалить через N дней | `180`, `1095` |
| `AUDIT_RETENTION_DAYS`, `BAN_HISTORY_RETENTION_DAYS` | журнал администратора и история блокировок | `1095`, `1095` |
| `SHARING_CONFIG`, `SHARING_TIMEZONE` | веса и пороги подсказок о шаринге (JSON), часовой пояс | см. `src/admin/sharingConfig.js`, `Europe/Moscow` |
| `ADMIN_LOGIN`, `ADMIN_PASSWORD_HASH` | администратор (логин может быть кириллицей; хэш — `npm run hash-password`) | вход админа выключен |
| `ADMIN_CONTACT` | контакт для заблокированных пользователей | — |
| `HOST_SITE_URL` | куда ведёт кнопка «Создать свою игру» на сайте игрока | `/host/` или первый из `HOST_SITE_ORIGIN` |
| `DATA_FILE` | JSON-файл с играми из версии без аккаунтов: переносятся в БД при старте | `./data/quizzes.json` |
| `IMAGE_QUOTA_MB` | сколько мегабайт картинок может хранить один аккаунт | `50` |
| `BACKUP_ENCRYPTION_KEY` | ключ шифрования бэкапов (32 байта) — без него бэкапы выключены | — |
| `GOOGLE_DRIVE_CLIENT_ID`, `GOOGLE_DRIVE_CLIENT_SECRET`, `GOOGLE_DRIVE_REFRESH_TOKEN` | доступ к Google Drive для бэкапов (`npm run google-drive-auth`) | — |
| `BACKUP_INTERVAL_HOURS`, `BACKUP_KEEP`, `BACKUP_DIR` | частота, сколько копий хранить, папка вместо Google Drive | `24`, `14`, — |
| `TRUST_PROXY` | `true`, если сервер за прокси (Render, Railway, nginx) | `false` |
| `TRUST_PROXY_HOPS` | сколько прокси перед сервером: IP берётся N-м справа в `X-Forwarded-For` | как `TRUST_PROXY` |
| `CLIENT_IP_MODE`, `CLIENT_IP_HEADER` | `header` — IP из заголовка доверенного прокси (например, `cf-connecting-ip`) | `hops` |
| `HOST_RECONNECT_MS` | сколько ждать ведущего после отключения, прежде чем закрыть комнату | `15000` |
| `PLAYER_RECONNECT_MS` | сколько ждать игрока в лобби, прежде чем убрать его из списка | `30000` |
| `MAX_PLAYERS_PER_ROOM`, `MAX_ROOMS` | ограничения | `100`, `500` |

Адрес сервера для сайтов задаётся в `host-site/js/config.js` и `player-site/js/config.js` (константа `PRODUCTION_SERVER_URL`). Если она пустая, сайт ищет сервер на том же хосте на порту 3000 — для локальной работы ничего менять не нужно.

### Камера работает только по HTTPS

Браузеры дают доступ к камере (`getUserMedia`) только в «безопасном контексте»: по **HTTPS** или на **localhost**.

* На компьютере через `http://localhost:5501` камера работает.
* Если открыть сайт игрока с телефона по адресу локальной сети (`http://192.168.x.x:5501`), камеры не будет. Тогда сайт сам предложит запасной вариант — загрузить фото (`<input type="file" capture="user">`): на телефоне он тоже откроет камеру, а фото всё равно обязательно.
* Чтобы проверить настоящее селфи с телефона, откройте сайты через HTTPS-туннель (например, `cloudflared tunnel --url http://localhost:5501` и такой же туннель для сервера) или задеплойте проект (см. ниже). Не забудьте добавить HTTPS-адреса в `HOST_SITE_ORIGIN`/`PLAYER_SITE_ORIGIN` и прописать адрес сервера в `config.js`.

## Как проверить каждую часть

### 1. Сервер

```bash
cd quiz-project/server
TEST_DATABASE_URL=postgresql://postgres:postgres@localhost:5432/luminous_test npm test
                                       # 81 тест: аккаунты и сессии, CSRF, лимиты, восстановление доступа, админ из окружения,
                                       # чужие игры, журналы, блокировки, админ-консоль, подсказки о шаринге, бэкапы,
                                       # безопасность (CSP, инъекции, права на каждом маршруте), полный цикл игры, наплыв игроков
npm start
curl http://localhost:3000/health      # {"status":"ok","db":"ok","rooms":0,...}
curl http://localhost:3000/api/quizzes # 401 — без входа игры не отдаются
npm run loadtest                       # нагрузочный тест: 80 игроков из одной сети, сбой сети, ответы
node scripts/loadtest.js https://ваш-сервер 150   # то же против задеплоенного сервера
npm run loadtest:rooms -- http://localhost:3000 50 40   # 50 игр одновременно по 40 игроков (2000 человек), у каждого свой IP и задержка сети
                                       # на сервере: TRUST_PROXY_HOPS=1, REGISTRATIONS_PER_IP_PER_HOUR=1000, REGISTRATIONS_PER_HOUR=10000
```

Каждый файл тестов работает в своей схеме базы `TEST_DATABASE_URL` и удаляет её после себя. Интеграционные тесты поднимают сервер на случайном порту и проверяют: регистрацию и вход (одинаковая ошибка для неизвестного логина и неверного пароля, новая сессия при входе, отзыв сессий при выходе и смене пароля), блокировку подбора пароля, CSRF, администратора только из окружения, CRUD игр и изоляцию по аккаунту, CORS, создание комнаты, вход игроков (уникальный ник, обязательное и проверенное фото), команды ведущего только от его сокета, фазу чтения (варианты не уходят раньше времени), вопросы с ответом вручную, один ответ на вопрос, отказ в ответе после таймера, подсчёт очков, скрытие мест после последнего вопроса, церемонию награждения по шагам, загрузку картинок, вход 60 игроков с одного IP и их возврат после сбоя, закрытие комнаты при уходе ведущего, переподключение ведущего и игрока, удаление игрока.

### 2. Сайт ведущего

1. Откройте http://localhost:5500 → «Открыть демо» (или «Создать новую»).
2. У вопроса переключите тип «Варианты ответа» / «Ввод ответа», задайте время на чтение и на ответ.
3. Попробуйте очистить название и нажать «Запустить» — появится список ошибок и подсветка полей.
4. Нажмите «Сохранить» → вернитесь на главную: игра появилась в списке.
5. «▶ Запустить» → откроется лобби с крупным 6-значным кодом. Новый запуск — новый код.

### 3. Сайт игрока

1. Откройте http://localhost:5501 во втором окне (или в режиме телефона в DevTools), введите код из лобби.
2. Сделайте селфи или выберите фото из галереи — пока фото нет, «Продолжить» неактивна.
3. Введите ник — в лобби ведущего игрок появится с аватаром и анимацией. Второй игрок с тем же ником получит ошибку.
4. Ведущий жмёт «Старт» → сначала все видят только вопрос (время на обдумывание), затем появляются варианты или поле для ответа. После ответа или окончания таймера — экран «Верно / Неверно / Время вышло» с очками и местом.
5. После последнего вопроса места скрыты. На странице итогов ведущий запускает церемонию: 3-е, 2-е и 1-е место появляются по очереди, и каждый игрок узнаёт своё место на телефоне в тот же момент, когда оно появляется на экране.
6. Закройте вкладку ведущего — через `HOST_RECONNECT_MS` игроки увидят «Ведущий отключился».

## Как устроена игра

### Логика ведущего

* Игру создают в редакторе: название и до 50 вопросов. Вопрос бывает двух типов:
  * **варианты ответа** — 2–4 варианта, один правильный;
  * **ввод ответа** — игрок пишет ответ сам; ведущий указывает 1–5 правильных вариантов. Регистр, «ё», знаки препинания и небольшие опечатки не учитываются (числа — только точно).
* У каждого вопроса: время на ответ (5–120 с), время на чтение (0–15 с — сколько игроки видят только вопрос, прежде чем появятся варианты) Картинки к вопросам отключены (они нагружали сервер и базу).
* Новую игру можно сразу запустить без сохранения, а сохранить после финала кнопкой «Сохранить игру». Сохранённые игры видны списком на главной; каждый запуск создаёт новую комнату с новым кодом.
* Результаты прошлых игр и фото игроков нигде не сохраняются: они живут только в памяти, пока открыта комната.
* Игры привязаны к браузеру ведущего: при первом входе браузер создаёт секретный токен и хранит его в `localStorage`. Сервер хранит только SHA-256 токена.
* Лобби, игра и итоги — отдельные страницы. При переходе страница заново подключается и «забирает» комнату событием `host:resume` с секретным ключом комнаты (`hostKey`). Пока ведущий переходит между страницами, сервер ждёт его `HOST_RECONNECT_MS`; если он не вернулся — комната закрывается, игроки получают уведомление.
* В лобби по клику на игрока его можно удалить (например, за неподходящее фото).
* Во время чтения кнопка «Показать варианты» открывает их сразу, во время ответов «Завершить вопрос» закрывает вопрос досрочно.
* Победители не раскрываются раньше времени: после последнего вопроса ни ведущий, ни игроки не видят мест и счёта. Итоги показывает церемония награждения, которой управляет ведущий.

### Логика игрока

1. Код комнаты — сервер проверяет, что комната есть и игра не началась.
2. Фото — селфи с камеры (`getUserMedia({ video: { facingMode: "user" } })`) или любое фото из галереи. Центр кадра сжимается до 200×200, JPEG, качество 0.7 (обычно 5–15 КБ).
3. Ник — 2–16 символов: буквы, цифры, пробел, `_ - .`; уникален в комнате без учёта регистра.
4. Всё уходит одним событием `player:join` (код, ник, фото base64).
5. Экран ожидания → вопрос (время на обдумывание) → кнопки ответа или поле ввода → результат после каждого вопроса → ожидание церемонии → своё место. При обрыве связи, блокировке экрана или перезагрузке страницы игрок сам возвращается в игру по токену (`player:rejoin`) с сохранёнными очками.

### Очки

Неправильный ответ — 0. Правильный — от 500 до 1000: `1000 × (1 − время_ответа / время_вопроса / 2)`. Время меряет сервер от момента, когда открылись варианты (после фазы чтения), до получения ответа. Одинаковые очки — одинаковое место.

### События Socket.IO

Полное описание форматов — в [PROTOCOL.md](PROTOCOL.md).

| Направление | Событие | Данные |
|---|---|---|
| ведущий → сервер | `host:create` | `{ quizId }` или `{ quiz }` → `{ code, hostKey, snapshot }` |
| ведущий → сервер | `host:resume` | `{ code, hostKey }` → `{ snapshot }` |
| ведущий → сервер | `host:start`, `host:next` | — (`host:next`: при чтении открывает варианты, при ответах закрывает вопрос, на результатах — дальше) |
| ведущий → сервер | `host:reveal` | `{ count? }` — показать следующее место на церемонии → `{ revealed, total }` |
| ведущий → сервер | `host:kick`, `host:close` | `{ playerId }` / — |
| игрок → сервер | `player:join` | `{ code, nickname, photo }` → `{ playerId, token, snapshot }` |
| игрок → сервер | `player:rejoin` | `{ code, token }` → `{ snapshot }` |
| игрок → сервер | `player:answer` | `{ questionIndex, answer }` — номер варианта или текст |
| сервер → клиенты | `lobby:update` | ведущему `{ action: join/update/leave, player, count }`, игрокам `{ count }` |
| сервер → клиенты | `game:started`, `question` (фазы `reading` и `answering`), `question:progress`, `results` | ход игры (варианты приходят только после чтения, правильный ответ — только в результатах) |
| сервер → клиенты | `game:ceremony`, `game:end` | ожидание церемонии; место игрока — только когда ведущий его показал |
| сервер → клиенты | `room:closed`, `player:kicked`, `error` | закрытие комнаты, удаление игрока, ошибка без callback |

Каждый запрос клиента получает ответ через acknowledgement: `{ ok: true, ... }` или `{ ok: false, error, code }`.

### Безопасность и надёжность

* Ведущий — вошедший аккаунт. Сессия хранится в БД, в браузере — только HttpOnly-cookie (`SameSite=Lax`, `Secure` и префикс `__Host-` на HTTPS); при входе выдаётся новая сессия, выход и смена пароля отзывают сессии. Пароли — argon2id, резервные коды — только хэшем. Изменяющие запросы проверяются по `Origin` и CSRF-токену. Лимиты попыток входа и регистрации хранятся в БД и переживают перезапуск.
* Роль и владелец берутся только из сессии на сервере. Администратор задаётся только переменными окружения.
* Content-Security-Policy без `unsafe-inline` и `unsafe-eval`: скрипты только с нашего сайта (библиотека QR лежит в `host-site/js/vendor/`), стили — свои и Google Fonts, соединения — только с этим сервером, встраивание во фреймы запрещено. Стили из JavaScript задаются только объектом (через CSSOM), не строкой. Квота картинок на аккаунт — `IMAGE_QUOTA_MB` (50 МБ).
* Журнал заходов (вход в аккаунт, регистрация, восстановление, создание игры, запуск комнаты, вход в комнату по коду) пишется в БД: посетитель, аккаунт, ник, код комнаты, IP, user-agent, тип устройства, ОС, браузер. Через `EVENTS_ANONYMIZE_DAYS` записи обезличиваются, позже удаляются. Доступ — только у администратора.
* Блокировки ставит только администратор: аккаунт, устройство и/или IP (подсеть не шире /24 и /48), с причиной и сроком или навсегда. Проверка при входе, регистрации, на защищённых запросах, при подключении Socket.IO, входе в комнату и перед игровыми событиями (по списку в памяти — без нагрузки на БД во время игры). Новая блокировка сразу убирает игрока из комнаты, а комнату заблокированного ведущего закрывает; пользователь видит экран «Вы заблокированы» с причиной, сроком и контактом администратора. Снятие не удаляет историю.
* Подсказки о совместном использовании аккаунтов — только для глаз администратора: сервер по ним ничего не делает сам. Переключатель хранится на сервере и по умолчанию выключен; выключен — оценка не считается и база GeoIP не загружается. Сигналы, веса и пороги — в `server/src/admin/sharingConfig.js`; местоположение по IP — локальная база geoip-lite (данные GeoLite от MaxMind), без внешних сервисов.
* Восстановление доступа без почты: логин + резервный код (выдаётся при регистрации, показывается один раз) или одноразовый код от администратора (срок `RECOVERY_CODE_TTL_MINUTES`, 5 попыток, новый код отзывает прежние). Ответ не выдаёт, существует ли логин; попытки ограничены. После сброса все сессии отозваны, старые коды не действуют, выдаётся новый резервный код. Пароли и коды нигде не показываются повторно и не пишутся в логи; в БД — только хэши.
* Команды `host:*` принимаются только от сокета, который сейчас управляет комнатой: создавшего её или вернувшегося с `hostKey` **и** тем же аккаунтом; сессия перепроверяется перед `host:create` и `host:resume`.
* Сервер проверяет всё: код (6 цифр), ник (длина, символы, уникальность), фото (только `data:image/jpeg|png;base64`, до 100 КБ, проверка сигнатуры файла), номер вопроса и ответа, структуру игры.
* Один ответ на вопрос; ответы после окончания таймера отклоняются (`TOO_LATE`).
* CORS: игры (`/api/quizzes`) доступны только сайту ведущего, проверки комнаты — обоим сайтам. Для WebSocket сервер сам проверяет заголовок `Origin`.
* Ограничение частоты: подбор кода комнаты (неверные коды с одного IP), создание комнат, любые события одного сокета. Успешные входы и возврат в игру по IP не ограничиваются — см. ниже.
* Картинки проверяются по содержимому файла (JPEG/PNG/WebP, до 1 МБ), отдаются с `nosniff`; неиспользуемые удаляются автоматически через 48 часов.
* Пользовательский текст вставляется в страницу только через `textContent`.
* Ограничен размер сообщений Socket.IO (256 КБ) и JSON-запросов.
* Старые комнаты удаляются автоматически (через 15 минут после финала, любые — через 6 часов).

### Много игроков одновременно

Раньше при наплыве игроков «терялось соединение». Причина была не в нагрузке (сервер отвечает за единицы миллисекунд), а в лимитах по IP: все телефоны в одной Wi-Fi сети (или за прокси хостинга) выходят в интернет с одного адреса. Сервер считал их одним человеком: после 20 входов и 60 проверок кода в минуту остальным отказывал, а после короткого сбоя сети никто не мог вернуться в игру — переподключение расходовало тот же лимит, и телефон сдавался. Нагрузочный тест (`npm run loadtest`): было — из 80 игроков вошли 20, после сбоя вернулись 0 из 20; стало — 180 из 180 вошли, вернулись и ответили на все вопросы.

Что сделано:

* по IP считаются только неверные коды комнат (защита от подбора), успешные входы не ограничены;
* возврат в игру по секретному токену не ограничен по IP;
* мягкие пинги Socket.IO (25/20 с) — телефоны с погасшим экраном и переключением сетей не отваливаются;
* игрок, отключившийся в лобби, остаётся в комнате 10 минут;
* клиенты при временных ошибках повторяют попытку сами, а при возвращении на вкладку сразу переподключаются;
* страница ведущего раз в несколько минут «пингует» сервер, чтобы бесплатный хостинг не уснул посреди игры;
* вместимость комнаты по умолчанию — 200 игроков (`MAX_PLAYERS_PER_ROOM`).

## Деплой

Рекомендуемый вариант — **Render одним сервисом с базой PostgreSQL** по Blueprint (`render.yaml` в корне
репозитория): веб-сервис Starter + Postgres Basic-256mb, миграции перед каждым деплоем, health check,
ежедневные зашифрованные бэкапы в Google Drive с проверкой восстановления.
Пошагово — [`docs/DEPLOY.md`](docs/DEPLOY.md).

После деплоя: игроки — `https://<адрес>/`, ведущий — `https://<адрес>/host/`, администратор — `https://<адрес>/admin/`.

**Раздельный деплой сайтов** (сервер и два статических сайта отдельными сервисами) возможен только на
одном домене — например, `play.example.com`, `host.example.com` и `api.example.com`: cookie сессии
(`SameSite=Lax`) между разными сайтами не передаются, а поддомены `*.onrender.com` браузеры считают
разными сайтами. В этом случае задайте `HOST_SITE_ORIGIN`, `PLAYER_SITE_ORIGIN`, `HOST_SITE_URL`
и подставьте адрес сервера в `js/config.js` сайтов (`tools/serve.js` делает это из `SERVER_URL`).
Сервису нужен `DATABASE_URL`; диск для файлов больше не нужен — всё хранится в базе.

## Как развивать проект

### Хранилище

Сервер работает с базой только через `server/src/db/index.js` (`query`, `one`, `many`, `tx`; все запросы параметризованы). Игры и картинки — в `server/src/stores/` (`PgQuizStore`, `PgImageStore`) с теми же методами, что у прежних `JsonQuizStore` и `ImageStore`, поэтому `QuizService` и игровая логика от хранилища не зависят. Изменения схемы — только новыми файлами `server/migrations/NNN_название.sql`: применённая миграция не меняется, данные не удаляются.

### Аккаунты

Владелец игр определяется сервером по cookie сессии (`server/src/identity/`): HTTP — `req.identity.account`, Socket.IO — `socket.identity.account`. Остальной код работает только с `owner.id` (UUID аккаунта). Игры из версии без аккаунтов (владелец — токен браузера) переносятся в аккаунт кнопкой «Перенести в мой аккаунт» на главной ведущего в том же браузере.

### Новые функции ведущего

Сайт ведущего разбит на модули: `api.js` (REST), `socket.js` (подключение и восстановление комнаты), `session.js` (состояние вкладки), `ui.js` (общие элементы), по одному модулю на страницу. Новое событие добавляется в трёх местах: обработчик в `server/src/sockets.js`, логика в `server/src/game.js` (если касается хода игры), подписка на странице ведущего.
