# Деплой Luminous на Render

Один веб-сервис (сервер + сайт игрока `/` + сайт ведущего `/host/` + админ-консоль `/admin/`) и база
PostgreSQL. Всё описано в `render.yaml` в корне репозитория (Blueprint).

| Что | План Render | Цена в месяц |
|---|---|---|
| Веб-сервис `luminous` | Starter (512 МБ, не засыпает) | $7 |
| База `luminous-db` | Postgres Basic-256mb, диск 1 ГБ | $6 + ≈$0,30 за диск |
| Итого | | ≈ $13,3 |

Секреты (пароль администратора, ключ шифрования бэкапов, доступ к Google Drive) **в репозиторий не
попадают**: в `render.yaml` у них стоит `sync: false`, значения вводятся в панели Render.
Репозиторий публичный — не вставляйте секреты ни в код, ни в коммиты.

---

## Шаг 1. Подготовка на своём компьютере

Нужен Node.js 22 или 24.

```bash
git clone <репозиторий> && cd <репозиторий>/quiz-project/server
npm install
```

1. **Хэш пароля администратора** (сам пароль никуда не записывается):
   ```bash
   npm run hash-password
   ```
   Пароль — не короче 12 символов. Скрипт печатает строку `$argon2id$…` — это `ADMIN_PASSWORD_HASH`.
2. **Ключ шифрования бэкапов:**
   ```bash
   node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
   ```
   Это `BACKUP_ENCRYPTION_KEY`. **Сохраните его в менеджер паролей.** Без ключа копии не прочитать,
   а если ключ пропадёт вместе с аккаунтом Render, копии в Google Drive станут бесполезны.

## Шаг 2. Доступ к Google Drive (для бэкапов)

Бэкапы шифруются на сервере и складываются в папку «Luminous backups» на вашем Google Диске.
Приложение получает доступ **только к файлам, которые создало само** (scope `drive.file`), а не ко всему Диску.
Если копии уже лежали в папке «AL Studio backups» (старое название проекта), сервер сам переименует её
в «Luminous backups» при следующей копии — старые и новые копии останутся вместе.

1. Откройте https://console.cloud.google.com → создайте проект (например, «Luminous backups»).
2. «APIs & Services» → «Library» → **Google Drive API** → «Enable».
3. «OAuth consent screen» (Google Auth Platform):
   * тип пользователей — **External**, название приложения, ваша почта;
   * «Data access» / «Scopes» → добавьте `https://www.googleapis.com/auth/drive.file`;
   * «Audience» → **Publish app** («In production»). Это важно: у приложения в режиме «Testing» Google
     отзывает токен через 7 дней. Для `drive.file` проверка приложения Google не нужна.
4. «Credentials» → «Create credentials» → «OAuth client ID» → тип **Desktop app**.
   Получите `Client ID` и `Client secret`.
5. На своём компьютере (папка `quiz-project/server`):
   ```bash
   GOOGLE_DRIVE_CLIENT_ID=… GOOGLE_DRIVE_CLIENT_SECRET=… npm run google-drive-auth
   ```
   Откройте показанную ссылку, войдите в Google-аккаунт, где будут храниться копии, разрешите доступ.
   В терминале появится `GOOGLE_DRIVE_REFRESH_TOKEN`.

## Шаг 3. Создание сервиса и базы

1. Render → **New → Blueprint** → подключите репозиторий → выберите ветку с игрой.
2. Render покажет два ресурса: `luminous` (Web Service, Starter) и `luminous-db` (Postgres Basic-256mb).
   Регион в `render.yaml` — Frankfurt (ближе к России); при желании поменяйте **до** первого создания.
3. Заполните переменные с `sync: false`:

   | Переменная | Значение |
   |---|---|
   | `ADMIN_LOGIN` | логин администратора (можно кириллицей) |
   | `ADMIN_PASSWORD_HASH` | строка из шага 1.1 |
   | `BACKUP_ENCRYPTION_KEY` | ключ из шага 1.2 |
   | `GOOGLE_DRIVE_CLIENT_ID`, `GOOGLE_DRIVE_CLIENT_SECRET` | из шага 2.4 |
   | `GOOGLE_DRIVE_REFRESH_TOKEN` | из шага 2.5 |

   Остальное Render выставит сам: `DATABASE_URL` (внутренний адрес базы), `SESSION_SECRET`
   (случайный), `NODE_VERSION=24`, `SERVE_SITES=true`, `ADMIN_CONTACT`, `TRUST_PROXY_HOPS=1`.
4. «Apply». Render соберёт сервис (`npm ci`), выполнит миграции (`preDeployCommand: npm run migrate`),
   запустит сервер и дождётся `GET /health`.

База доступна только из внутренней сети Render (`ipAllowList: []`) — снаружи к ней не подключиться.

## Шаг 4. Проверка после деплоя

1. `https://<адрес>/health` → `{"status":"ok","db":"ok",…}`.
2. `https://<адрес>/` — сайт игрока с кнопкой «Создать свою игру».
3. `https://<адрес>/host/` → страница входа. Зарегистрируйте тестовый аккаунт, сохраните резервный код,
   откройте демо, запустите игру, войдите игроком с телефона по коду.
4. `https://<адрес>/admin/` → войдите администратором. Должны быть видны аккаунт и гость-игрок,
   строка «Резервные копии…». Нажмите **«Сделать копию сейчас»** → «проверена после загрузки»;
   в Google Диске появится папка «Luminous backups» с файлом `luminous-….alsb`.

## Шаг 5. Проверка IP за прокси (обязательно)

Сервер берёт IP клиента как `TRUST_PROXY_HOPS`-й адрес **справа** в `X-Forwarded-For` (первый адрес
заголовка клиент может подделать). Проверьте на реальном деплое:

1. Войдите администратором и откройте в том же браузере `https://<адрес>/api/admin/diagnostics/ip`.
   `computedIp` должен совпадать с вашим внешним IP (сравните с https://ifconfig.me).
2. Попытка подделки: в браузере, где вы вошли как администратор, откройте консоль разработчика на любой
   странице сайта и выполните
   ```js
   fetch('/api/admin/diagnostics/ip', { headers: { 'X-Forwarded-For': '1.2.3.4' } }).then((r) => r.json()).then(console.log)
   ```
   `computedIp` **не** должен стать `1.2.3.4`, а `xForwardedFor` покажет, куда Render поставил ваш адрес.
3. Если `computedIp` — внутренний адрес вида `10.x.x.x`, увеличьте `TRUST_PROXY_HOPS` на 1;
   если удалось подставить `1.2.3.4` — уменьшите. После изменения переменной Render перезапустит сервис.
4. Альтернатива: если в `headers` есть `cf-connecting-ip` с вашим адресом, и подделать его тем же
   способом (`headers: { 'CF-Connecting-IP': '1.2.3.4' }`) **не** удаётся, можно включить
   `CLIENT_IP_MODE=header` и `CLIENT_IP_HEADER=cf-connecting-ip`.

От правильного IP зависят лимиты подбора пароля, блокировки по IP и журналы.

## Бэкапы и восстановление

**Три уровня защиты данных:**

1. **Render Postgres (платный план):** восстановление на момент времени (PITR, несколько последних дней)
   и ручной экспорт в панели базы → «Recovery» / «Exports». Это первое, к чему обращаться при ошибке.
2. **Ежедневная зашифрованная копия в Google Drive** (сервер делает её сам раз в `BACKUP_INTERVAL_HOURS`,
   хранит `BACKUP_KEEP` последних): логический дамп всех таблиц в одной транзакции → gzip → AES-256-GCM
   → загрузка → **скачивание обратно и сверка со сводкой** (количество строк и SHA-256 каждой таблицы).
   Состояние видно в админ-консоли. Сессии в копию не входят — после восстановления пользователи входят заново.
3. **Проверка восстановления** — раз в месяц (и после изменения схемы): Render → `luminous` → **Shell**,
   перейдите в папку сервера (`cd quiz-project/server` или `cd server` — смотря где откроется Shell, проверьте `ls`):
   ```bash
   npm run restore-check
   ```
   Скрипт скачивает самую свежую копию, разворачивает её во **временную схему** той же базы, сверяет суммы
   всех таблиц со сводкой и удаляет схему. Рабочие данные не затрагиваются. Ожидаемый вывод:
   `[restore-check] OK: восстановлено строк …, все 11 таблиц совпадают`.

**Полное восстановление после аварии** (база потеряна или испорчена):

1. Render → New → PostgreSQL (тот же план и регион) → скопируйте его **Internal Database URL**.
2. Render → `luminous` → Shell, в папке сервера:
   ```bash
   DATABASE_URL='<Internal URL новой базы>' npm run restore -- --latest --yes
   ```
   (или `--file путь.alsb` для конкретной копии; в непустую базу скрипт не пишет).
3. В Environment сервиса замените `DATABASE_URL` на адрес новой базы → сервис перезапустится.
4. Проверьте `/health` и вход администратора.

Локально (на своём компьютере) копию можно проверить так же: скачайте файл `.alsb` из Google Drive и
выполните `BACKUP_ENCRYPTION_KEY=… DATABASE_URL=<локальная база> npm run restore-check -- --file файл.alsb`.

## Обновления

* Новая версия — push в ветку, подключённую к Blueprint. Render собирает её, выполняет миграции
  (`preDeployCommand`), запускает и переключает трафик только после успешного `/health`.
* Миграции только добавляют таблицы и столбцы и выполняются под блокировкой в одной транзакции: если что-то
  пошло не так, схема остаётся прежней, деплой отменяется, старая версия продолжает работать.
* Идущие в момент деплоя игры хранятся в памяти сервера и завершаются (игроки увидят «Сервер перезапускается»).
  Обновляйте между мероприятиями. Сохранённые игры, аккаунты и журналы не теряются — они в базе.
* Сайт ведущего и игрока переподключаются к серверу сами (Socket.IO с повторными попытками).

## Переменные окружения

Полный список с пояснениями — `quiz-project/server/.env.example`. Главное для Render:

| Переменная | Откуда |
|---|---|
| `DATABASE_URL` | Render, из базы `luminous-db` |
| `SESSION_SECRET` | Render генерирует (`generateValue`) |
| `ADMIN_LOGIN`, `ADMIN_PASSWORD_HASH` | вы (шаг 3) |
| `ADMIN_CONTACT` | `render.yaml` (почта поддержки, показывается заблокированным) |
| `BACKUP_ENCRYPTION_KEY`, `GOOGLE_DRIVE_*` | вы (шаги 1–3) |
| `TRUST_PROXY_HOPS`, `CLIENT_IP_MODE` | `render.yaml`, проверка — шаг 5 |
| `EVENTS_ANONYMIZE_DAYS`, `EVENTS_DELETE_DAYS`, `AUDIT_RETENTION_DAYS`, `BAN_HISTORY_RETENTION_DAYS` | по умолчанию 180 / 1095 / 1095 / 1095 дней |
| `SHARING_CONFIG`, `SHARING_TIMEZONE` | необязательно: веса подсказок о шаринге |

## Если что-то пошло не так

| Симптом | Что проверить |
|---|---|
| Деплой падает на `npm run migrate` | Логи деплоя: текст ошибки миграции. Старая версия продолжает работать. |
| «SESSION_SECRET не задан» | Environment сервиса: переменная должна существовать (Render создаёт её из Blueprint). |
| `/health` → `"db":"error"` | Состояние базы в панели Render; `DATABASE_URL` указывает на внутренний адрес. |
| Админ не может войти | `ADMIN_LOGIN` и `ADMIN_PASSWORD_HASH` (хэш целиком, начиная с `$argon2id$`). В логах — `[admin] вход администратора: …`. Вход в консоль — только с запомненных устройств (не больше `ADMIN_MAX_DEVICES`, по умолчанию 2): с нового устройства сайт отвечает «Неверный логин или пароль». Уберите старое устройство в консоли («Доступ к консоли») или, если доступа нет ни с одного, задайте `ADMIN_DEVICE_RESET` любым новым словом. |
| Ведущий не может создать игру | Создание своих игр — после оплаты: ведущий прикрепляет чек (окно оплаты на главной), доступ открывается сразу. Без оплаты доступна только демо-игра. Оплаты и чеки — вкладка «Оплаты» в консоли; отключить оплату — `PAYMENT_REQUIRED=false`. QR-код — файл `host-site/img/payment-qr.jpg`. |
| «Резервная копия НЕ удалась» в консоли | Текст ошибки там же. Чаще всего — токен Google (приложение осталось в режиме «Testing» или доступ отозван): повторите шаг 2.5. |
| Все игроки «с одного IP» | Шаг 5: неверный `TRUST_PROXY_HOPS`. |
